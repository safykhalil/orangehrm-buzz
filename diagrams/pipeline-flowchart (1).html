Milestone 4 was re-run once — both results are preserved

Live execution against a real, shared, uncontrolled environment can produce genuinely different results between runs — this is expected, and the audit trail keeps both, rather than silently overwriting history.

Run 1 (original)
20 PASS / 0 FAIL / 7 BLOCKED (policy). DEFECT-001 raised. Preserved in logs/session-log.md.
Run 2 + DEFECT-002 re-verification (final, active)
16 PASS / 2 PASS† / 1 FAIL / 8 BLOCKED. DEFECT-001 reconfirmed. DEFECT-002 (Like/Unlike) was investigated and withdrawn — a test-targeting error (the probe clicked a display-only icon, not the real Like control), not a product defect.

DEFECT-001 was reclassified after a QC-authorized live check (2026-09-28)

The Share Video button stays clickable with an empty URL — that fact, first found in Milestone 4, is unchanged. What changed: a live, one-time QC-authorized check (outside the formal milestone runs) monitored the network when Share was clicked with an empty field.

Before
Classified as a confirmed functional defect: button not disabled, unlike Share Photos.
After — UX inconsistency, not a functional defect
Clicking Share with an empty URL shows an inline "Required" message, fires zero network requests, and creates no post. The two Share dialogs simply use different (each individually valid) client-side validation patterns. Original finding kept in the report for audit, not deleted.

Milestone 5 caught two real issues before they caused wrong results

3 automation bugs (H-01–H-03)
A crashed write-guard, a hidden-vs-visible locator mismatch, an over-strict DOM-removal check. All in the scripts, not the product — healed, logged with before/after.
1 environmental-drift bug, caught pre-emptively (H-04)
The shared demo's date format varies between sessions (Y-d-m vs Y-m-d). The parser now reads the app's configured format at runtime instead of assuming one — caught before it silently mis-ordered results.
Interaction Policy note: this is a shared public demo instance. Every skill from M2 onward carries forward the same rule — actions that create permanent, visible-to-others content (posting, commenting, uploading) are excluded by default and logged as such, rather than attempted or silently skipped. This is why 7 of 27 designed cases show as policy-blocked in M4 (plus 1 more blocked by the automation tool's own permission classifier — a tooling limitation, not policy or app behavior), and why 6 of the original automation candidates were reclassified from Needs Automation = Yes to No after QC review. DEFECT-001's Milestone 5 automation is a regression probe with an inverted assertion (PASS = defect still present) — never an ordinary pass/fail gate.
